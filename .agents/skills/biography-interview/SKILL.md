# Biography interview

The biography is only as good as what the user has told it, and most of what
makes a strong application (impact, numbers, stories, honest skill depth) lives
in the user's memory until someone asks. This skill is how it gets asked.

## Before asking anything

Read `biography.md` in full, and any material the user has provided that isn't
in it yet: a resume, a LinkedIn export, links, documents. Fold what you learn
into the biography first. The user's patience is the scarce resource, and a
question about something already written down spends it for nothing.

## Order: broad before deep, highest value first

You don't know how much patience the user has, and they may stop at any point.
Order the questions so that stopping anywhere leaves the biography as useful as
it could be by then. Typically:

1. The skeleton: each role with dates, title, and a sentence on what the job
   was. What they want next, and what they want to avoid.
2. For each role, the one or two things they're proudest of, and any numbers
   attached.
3. Skills, and honestly how deep each goes.
4. Stories in detail, the context around each role, and the long tail.

On a later pass, start wherever the biography is thinnest relative to what the
user's search needs. The "Suggested questions" section may help, but you
aren't bound to it. A fresh look may find better questions.

## How to ask

- A few questions at a time, never a wall of them.
- Accept "I don't remember" and "skip" without pushing, and note the gap.
- Press gently on every story for impact: what changed because of the user's
  work, and by how much. Most engineers don't track it, so an estimate they can
  defend is fine, recorded as an estimate.
- Ask how deep a skill goes in terms the user can answer: could they explain
  it to a skeptical interviewer, build something new with it, or only
  recognize it?
- Notice and record claim boundaries: shared credit, confidential details,
  anything the user is unsure of.

## Writing it down

Write answers into the biography as you go, not at the end, so nothing is lost
if the session stops. Put each fact in the most specific place it belongs,
once. If an answer changes something other documents relied on, reconcile them
(see `README.md`, "Updating facts").

## When the interview stops

If there's more worth asking, leave the questions you would have asked next in
the biography's "Suggested questions" section. They're a hint for a later
session, not a script for it.
